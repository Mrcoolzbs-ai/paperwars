## 1. Видение продукта

Paper Wars: Rebirth — многопользовательская пошаговая военно-политическая стратегия с управлением государством, экономикой, территорией, культурой, религией, идеологией, дипломатией и армией. Важная часть игрового опыта — исследование руин и постепенное раскрытие скрытой истории мира.

Ключевое техническое свойство — детерминированный Simulation Engine: одинаковые версия правил, состояние, подтверждённые приказы и RNG-контекст должны давать одинаковый результат. Web, API, worker и CLI являются внешними интерфейсами к игровому ядру, а не местом реализации игровых правил.

### 1.1. Принципы проекта

1. **Правила отделены от реализации.** Нормативный Baseline и версионируемые ruleset — источники игровых решений.
2. **Происхождение правил явно.** Механики классифицируются как CONFIRMED, INFERRED, NEW DESIGN или PROPOSAL.
3. **Детерминированная симуляция.** Нет глобального RNG, скрытых обращений к системному времени или сетевым сервисам внутри Domain/Simulation.
4. **Snapshot + event history.** Снимки используются для восстановления состояния, события — для хроники и аудита.
5. **Атомарная фиксация хода.** Один и тот же ход нельзя применить дважды или частично сохранить.
6. **PostgreSQL-backed jobs в MVP.** Redis не входит в MVP.
7. **Скрытая информация защищается на сервере.** Клиент получает DTO-проекции по правам государства.
8. **Неподтверждённый лор не становится каноном.** Q18–Q20 остаются сюжетными PROPOSAL до решения автора.

### 1.6. RNG и commit-reveal

- [x] CSPRNG-примитив генерации seed длиной 32 байта.
- [x] Создание seed первого хода подключено к транзакции создания кампании: campaign, owner membership и committed seed фиксируются одним COMMIT.
- [x] Commitment: канонический binary `commit-v1` с campaignId, turnNumber, rulesetVersion, rngVersion и seed.
- [x] HMAC-SHA-256 с доменами и версией `rng-v1`.
- [x] Канонический `enc-v1` length-prefixed encoding: campaignId/drawId uint16; rngVersion/domain uint8; turnNumber uint32 BE; attempt bigint uint64 BE.
- [x] Rejection sampling без modulo bias и без искусственного лимита попыток.
- [x] Стабильные draw IDs и транзакционный журнал random draws с проверкой повторного использования ID.
- [x] Хранение seed только AES-256-GCM ciphertext; ключ не попадает в БД.
- [x] AAD binary encoding с campaignId, turnNumber, rngVersion и encryptionKeyVersion.
- [x] Nonce 12 байт и auth tag 16 байт; UNIQUE `(encryption_key_version, nonce)`; retry только при конфликте по этой паре.
- [x] Версионированный сервис ключей; старые версии доступны для расшифрования.
- [x] Persistence-level gating: Worker-загрузчик читает committed seed, reveal разрешается только после `campaign.status = completed`; публичные API endpoints ещё не реализованы.
- [x] Тесты commitment, AAD, AES-GCM, nonce collision, кодирования префиксов 13/11/14 байт, uint32/uint64 границ, независимости доменов и отсутствия modulo bias.

### 1.8. Закрытие приказов, очередь и Worker

**Статус на 27 ноября 2026 года: транзакционное закрытие приказов, PostgreSQL queue/leases/fencing, атомарная финализация, polling lifecycle и отдельный production host реализованы.** Конкретный baseline resolver покрывает текущую часть подтверждённых действий; остальные фазы и механики остаются незавершёнными.

- [x] `closeOrders`: первой блокировкой берёт кампанию `FOR UPDATE`; проверяет статус, `orders_locked`, snapshot и актуальный список активных участников.
- [x] Проверяет подтверждения либо deadline по времени БД `clock_timestamp()`.
- [x] В одной транзакции финализирует `confirmed`, переводит `draft/unconfirmed` в `discarded`, включает `orders_locked` и создаёт TurnJob.
- [x] `confirmCampaignOrders` использует `FOR SHARE` на campaign; переводит draft/unconfirmed приказы страны участника в confirmed и отмечает membership в той же транзакции.
- [x] Создание, чтение, изменение и удаление собственных приказов текущего хода: `createCampaignOrder`, `listCampaignOrders`, `updateCampaignOrder`, `deleteCampaignOrder`. ### Порядок среды и экономического расчёта

1. PREPARE_TURN: установить год, сезон и контекст хода.
2. APPLY_ENVIRONMENT: наложить сезонные/климатические модификаторы **до** MOVE, BATTLE и ECONOMY.
3. VALIDATE → RESOLVE_CONFLICTS → MOVE → COLONIZE → BUILD → RESEARCH → DIPLOMACY → BATTLE.
4. ECONOMY: рассчитывать производство, доступные ресурсы, потребление обновлённого населения, дефицит, налоги, armyBudget и содержание.
5. SEASONAL_EVENTS: только в последний ход сезона; проверить шахты и осенние затопления для заканчивающегося сезона, затем перейти к следующему.
6. EVENTS → FINALIZE.

APPLY_ENVIRONMENT не удаляет поля и не переводит их в необратимое состояние. Зимой поле без действующей теплицы имеет эффективное производство еды 0; поле с теплицей производит согласно ruleset. Снег увеличивает стоимость движения в 2 раза. Иные климатические модификаторы влияют на движение, бой и производство только при наличии явного параметра ruleset.

Колонизация и завершённый снос создают жителей до ECONOMY. Восстановление COLLAPSED-шахты выполняется в BUILD и переводит её в ACTIVE до сезонной проверки.

### Definition of Done

- [x] Содержание генералов: 0–6 звёзд = 2, 3, 5, 8, 13, 21, 34 монеты за ход; включено в ArmyBudget и армейское содержание.
- [x] Формирование отрядов с одним генералом, 1–40 уникальными юнитами и защитой от повторного назначения бойца/командира.
- [x] Категории движения сохраняются у отряда: лёгкий 1–10 — 7 клеток; средний 11–20 — 5; тяжёлый 21–30 — 3; громадный 31–40 — 1.

- [ ] Инициатива и последовательность атак.
- [ ] Броски атаки через RNG-домен battle.
- [ ] Расчёт попаданий, брони и здоровья.
- [ ] Мораль и последовательные пороги 50%, 40%, 30%, 20%, 10% с фиксацией passedThresholds.

### Текущий инкремент и принятые defaults

- Генерал нанимается в казарме за 1 ОД. Архив не задаёт распределение качества, поэтому текущая реализация использует равномерный серверный d7 (0–6) из committed RNG; игрок не передаёт поле качества.
- Формирование отряда занимает 1 ОД; все выбранные бойцы и генерал должны быть размещены в одной казарме.
- Скорость и римская категория фиксируются при формировании; само перемещение пока не разрешено.

Бои и осады полностью детерминированы относительно сохранённого RNG-контекста, все результаты объяснимы по отчёту, а правила потерь и захвата не допускают неоднозначного состояния.

## 14. Порядок фаз хода (рабочая последовательность)

Последовательность после технического аудита:

1. PREPARE_TURN
2. APPLY_ENVIRONMENT
3. VALIDATE
4. RESOLVE_CONFLICTS
5. MOVE
6. COLONIZE
7. BUILD
8. RESEARCH
9. DIPLOMACY
10. BATTLE
11. ECONOMY
12. SEASONAL_EVENTS
13. EVENTS
14. FINALIZE

Критические зависимости:
- APPLY_ENVIRONMENT действует до MOVE, BATTLE и ECONOMY.
- COLONIZE и завершённый BUILD дают новых жителей до ECONOMY.
- BUILD включает восстановление COLLAPSED-шахт; их состояние ACTIVE до ECONOMY/SEASONAL_EVENTS.
- SEASONAL_EVENTS запускается только в последний ход сезона и проверяет заканчивающийся внутриигровой сезон.
- Snapshot, события, random log, отчёты, следующий seed и завершение TurnJob фиксируются атомарно в persistence-слое.

### Реализация — ещё не завершена

- Полный lifecycle membership/roles, audit log критичных действий и rate limiting публичных auth endpoints остаются незавершёнными; admin-code throttling не равен общему rate limiting.

- В армии реализованы базовый roster, найм, генералы и отряды; MOVE, Battle, morale, siege и territorial conquest отсутствуют.
- Политические механики реализованы только на уровне выбора/хранения культуры, формы правления и официальной системы; численные социальные эффекты и политический цикл отсутствуют.
- Полные DTO-проекции мира по видимости и аудит всех endpoint/report/export на отсутствие закрытых данных ещё необходимы.
- Дипломатия, климатические события сверх текущих паводков, раскрытие лора, балансировка и релиз остаются незавершёнными.

- Definition of Done Stage 2 и полный end-to-end сценарий ещё не достигнуты; наличие Worker означает корректную обработку поддержанных типов приказов, а не завершение всей игры.
